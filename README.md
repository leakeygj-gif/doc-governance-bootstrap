# doc-governance-bootstrap

一个跨工具通用的 Agent Skill：**一次性**把一套经过真实项目打磨的「文档治理体系」种进任意代码仓库，减少 AI 改代码后遗漏文档更新的风险。

规则写进 `AGENTS.md`（跨工具中性约定，Codex 等直接读取），再由 `CLAUDE.md` 用 `@AGENTS.md` 机械导入——**规则只有一份，两类工具拿到的是同一套**，不是"写两份指望它们保持一致"。

## 它解决什么问题

AI 改完代码，文档没跟上。常见的失败形态有四种，本体系分别对应四条规则：

| 失败场景 | 对应规则 |
|---|---|
| 大改动没留下计划和验证证据，事后无法复核 | **任务立项规则**：按*验证复杂度*决定要不要立 Task，Plan + Report 成对 |
| 主对话陷进实现细节，丢失全局判断 | **分叉执行规则**：立了 Task 的任务交子代理执行，回归只报五项 |
| 改了代码没写日志，换个会话就接不上 | **交接日志规则** + `.githooks/pre-commit` **机械拦截** |
| 规格文档写死了参数的当前值，值一改文档就是错的 | **规格同步规则**：规格以*参数来源与设计意图*为主，必要值引用权威来源 |

## 装完你会得到什么

```
docs/specs/       # 系统规格：参数来源与设计意图，必要值引用权威来源
docs/tasks/       # Plan + Report 成对的任务文档 + 项目登记表
docs/refs/        # 外部参考资料索引
docs/HANDOFF.md   # 追加式交接日志，最新在最上
docs/WORKFLOW.md  # 协作流程 + 可随时手动执行的文档巡检清单
.githooks/pre-commit   # 启用后：源码变更未配日志文件更新 → 拒绝提交
tools/doc_symbols.py   # 规格文档符号词法疑点检查
tools/task_pairs.py    # 同目录配对、完整前缀/显式关联、状态及历史豁免检查
AGENTS.md         # 四条规则（CLAUDE.md 通过 @AGENTS.md 导入同一份）
```

## 怎么用

在目标仓库里调用这个 skill 即可，它会：

1. **访谈 3 个问题**（源码目录与文件类型 / 文档语言 / 可选的称呼约定）；
2. **探测现状**，已有模板检查兼容性后复用，冲突先确认处置；
3. **生成文件**，并把 `.githooks/pre-commit` 的源码匹配规则替换成你的实际路径；
4. **自检**：运行符号及 Task 检查，在隔离仓库实测生成的 hook；单独核验目标仓库启用状态；
5. **汇报**：逐条说明哪些新建、哪些跳过、哪些替换了旧规则。

每个克隆单独启用。先读取有效 `core.hooksPath`；已有其他路径时须确认整合方案，不能覆盖。配置操作获授权后可执行并回读，否则报告未启用并提供：

```bash
git config --local core.hooksPath .githooks
```

## 任务资料与已有项目

新任务集中在 `docs/tasks/P<编号>_<日期>_<任务名>/`：`plan.md`、`report.md`、专用脚本、清单与结果按需同放，文件少时不另分 tools/data 子目录。实际复用后再考虑提取公共工具；产品代码留源码，大型原始数据保留原位并引用。清单记录用途、参数、输入输出、校验和保存状态，历史平铺任务及资料不批量迁移。

计划状态和验收边界分开；一个总计划可显式关联多个阶段报告。检查器将自由状态和歧义列为待确认，有来源的历史豁免可显式配置，详见 [任务规则](docs/tasks/README.md) 与 [检查命令](docs/WORKFLOW.md)。

开发仓库、安装副本和项目生成文件不会自动同步。已有项目先按 [只读升级预览](references/upgrade-preview.md) 列差异和定制，再确认写入；保留项目已确认的约定，包括只用 AGENTS.md 的安排。

## 几个刻意的设计取舍

这些不是随手定的，每条背后都有一个真实项目里发生过的失败场景，详见 [`references/methodology.md`](references/methodology.md)：

- **立项判据是「验证复杂度」而非「改动规模」**——一个改动的验证需要表格、多组实测数据才讲得清，它才够格立 Task；一句话说得清的只写交接日志。按行数或耗时判断会把大量琐碎改动拖进重流程。
- **Report 定稿后，数据、方法与前提不再修改**——它们是证据，改了就是造假、也无法复核。结论与建议可以*追加*修订记录，只追加不覆盖；测出新数据就写新 Report，旧的保留为基线。
- **规格避免重复维护实现值**——以来源和设计意图为主；必要的协议常量、单位、兼容性边界、验收阈值通过权威来源引用或自动生成，并标明更新方式。
- **不设 `PROJECT_STATUS.md` 这类覆盖式状态快照**——状态应当从 `docs/tasks/` 的登记表派生，另开一份必然漂移（真实项目里出现过 42 条风险记录只剩极少数还成立的情况）。
- **只有能自动化验证的环节才配得上机械强制**——"源码变更未配日志文件更新"可以被已启用的 git hook 拦截，日志内容是否合格仍需审核；"这个改动够不够格立 Task"是判断题，目前仍靠自觉，不假装两者可靠程度相同。

## 已知边界

- 这是**初始化**动作，不做通用模板升级；已有模板需检查兼容性。未解决冲突前不写入不兼容的新规则，也不报告完整安装成功。
- 目标仓库已有的其他文档习惯（CHANGELOG、ADR 目录等）不会被自动整合或替代。
- Codex 等其他工具是否真的读 `AGENTS.md`、读了是否照做，取决于该工具自身实现，本 skill 无法代为验证。git pre-commit 不依赖 AI 配合，但必须启用且可以绕过；隔离实测不等于目标仓库完成真实提交验收。
- 符号检查是词法提醒，不验证归属或规格语义。检查器退出码 0 包含无对象，不能当作实际规格已验证；详细状态及 CLI 见 `docs/WORKFLOW.md`。

```
SKILL.md                  # skill 本体（执行步骤）

assets/templates/         # 会被装进目标仓库的模板文件
AGENTS.md                 # 本仓库自己的开发规则（自举：本项目也用这套体系管自己）
docs/                     # 本仓库自己的治理文档
```
