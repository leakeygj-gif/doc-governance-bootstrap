# docs/tasks/ — 任务文档目录

新任务按任务目录集中保存计划、报告和专用资料。一个总计划也可以对应多份阶段报告，通过明确链接关联，不要求每份报告另建计划。

## 命名规则

```text
docs/tasks/P<NN>_<YYYYMMDD>_<任务名>/
├── plan.md                  计划（做之前写）
├── report.md                验证报告（收口时写）
├── analyze.py               专用脚本（需要时）
├── manifest.json            资料清单（有额外资料时）
└── results/                 结果（需要时，复测分轮次）
```

- 目录名承担任务归属，文件少时直接放在目录内，不强制建立 `tools/`、`data/` 子目录或空占位文件。
- 阶段文件可用 `阶段名.plan.md`、`阶段名.report.md`；需要总览时使用同目录 `index.md`，不再嵌套任务目录。
- 开新任务取登记表最大序号 +1，序号不复用。跨任务的时间线由 `docs/HANDOFF.md` 承担。
- 历史平铺的 `P<NN>_<YYYYMMDD>_<名称>.plan.md` / `.report.md` / `.index.md` 继续有效；既有 `tools/tasks/`、`data/tasks/` 资料保持原位，不批量搬迁或改名。
- 序号只在本分支内唯一；会合并的分支须协调编号，不会合并的独立产品线可分别编号。

## 什么时候立 Task

判据是**验证产出的复杂度**，不是改了几个文件。

**够格立 Task** —— 验证需要表格、多组实测数据，或者不写方法说明就无法复核。
**不够格** —— 验证一句话说得清。这类改动只写一条完整的 `docs/HANDOFF.md` 记录，不进本目录。

**例外**：涉及生产环境变更、外部系统的真实写操作、物理设备动作等不可逆操作的任务，不看验证复杂度，**一律立 Task**，且分步计划必须拆成可分级门禁的步骤。

### plan 和 report 必须成对

**立 Task 就要有 plan 和 report，缺一不可。不值得写 report 的改动，也不该写 plan。**

- `plan` 在动手前写，未经确认不得实施
- `report` 在任务收口时写，定稿后按「report 定稿后怎么改」处理
- 执行中只有 plan 没有 report 是**正常状态**，由 plan 的状态字段区分，不算违规

只有 plan 没有 report 的**已完成**任务，先核查漏收口、关联缺失或状态误标。按真实证据补报告，无法复原的证据标明缺失，不编造或删计划消警。

同一任务目录的 `plan.md` / `report.md` 默认配对；阶段文件和历史平铺文件按完整前缀配对，编号相同不足以配对。阶段或复测报告可用独立行 `**对应计划**：[总计划](plan.md)` 显式关联，兼容旧字段 `**计划**`。链接相对所在 Markdown 文件解析。任务内 `index.md` 或历史 `.index.md` 可明确链接唯一总计划与阶段报告；多计划索引需逐表格行明确唯一计划与报告，否则逐报告声明。显式关联不要求另有同名前缀基线报告，报告存在不证明全部验收点已完成。

检查器仅扫描 `docs/tasks/` 根目录及其一级 `P<编号>_.../` 任务目录中的直接文档，不递归扫描 `results/` 或其他资料子目录。历史豁免的 `plan` 使用相对任务根目录的精确路径，例如 `P25_20260907_任务名/plan.md`。

### 状态与验收边界

新计划的 `**状态**` 只填一个固定值：草拟中 / 已确认 / 执行中 / 已完成 / 搁置 / 已废弃。补充说明放 `**验收边界**`：例如“本次离线修复已验证；硬件复扫未验证”。只有计划范围已完成才可标“已完成”；若硬件复扫本属本次验收点，则仍是“执行中”。历史复合状态保留原文，能识别的规范状态附注可兼容，自由或矛盾状态交人工确认，不批量重写历史。

### 任务资料默认集中保存

为哪个任务产生的脚本、结果和说明，就放进哪个任务目录。仅在实际被其他任务重复使用、逻辑基本相同时，考虑提取到公共 `tools/`；不要预先为可能复用建立分类。已有共享工具直接引用，产品运行代码仍放源码目录。大型原始扫描数据可保留统一存储位置，清单引用，不重复复制，也不强制入 Git。

复测在 `results/round-02/` 等新轮次目录保存产物，使用新的 `round-02.report.md` 显式关联计划；旧报告及其资料保留。文件增加到确有分组必要时再建子目录，计划、报告与索引仍直接放任务目录以供检查。

报告的资料表是阅读入口；有脚本、数据或结果时建立 `manifest.json` 清单。建议结构：`task` 为任务目录名或历史任务前缀，`plan`/`report` 为仓库相对路径，`artifacts` 中每项记录 `path`、`purpose`、`role`（script/input/output）、`parameters`、`inputs`、`outputs`、`sha256`、`storage`。路径默认相对仓库根，外部资料注明绝对路径或稳定归档地址；未知校验值写 null 并说明，参数不适用写空对象。`storage` 分别记录本机存在、Git 跟踪、外部归档是否核验，不能用“文件存在”代替“已备份”。收口时复查位置和校验值；共享脚本还需记录所用提交或校验值，避免后来改动后无法复算。

已定稿报告引用的清单与结果同样作为历史证据保留。复核脚本默认拒绝覆盖已有输出；复测使用新轮次目录，并在新报告中链接。共享脚本升级前，确保旧版本可从已提交的版本或保存的源码快照恢复；仅记录校验值不能恢复源码。

清单是资料索引，不是新的任务状态库；不重复报告实测表。敏感参数使用脱敏引用。没有额外资料的任务在报告注明“不适用”，不为满足结构造文件。历史任务按需补关联。

## 什么时候建 `index.md`

多个阶段需要总览时建；普通脚本和数据文件增加不要求建立索引。内容：目标、全局禁区、阶段进度表（含指向各阶段文件的链接）、已冻结的项目级决定、未完待续。

一句话：**index 回答"这条线是什么、走到哪了"，plan 回答"这一步打算怎么做"，report 回答"这一步实测出了什么"。**

## PLAN 模板

```markdown
# <任务名>

**创建日期**：YYYY-MM-DD
**状态**：草拟中 / 已确认 / 执行中 / 已完成 / 已废弃 / 搁置
**验收边界**：本次计划涵盖什么，哪些仍未验收
**项目**：P<NN> <项目名>
**关联 worker**：（分叉后填 agent id）

## 目标
要解决的具体问题、为什么现在做。

## 边界
本次改动可以触及的范围（文件 / 模块 / 行为）。

## 禁区
**只写本任务特有的约束**，以及需要沉淀的决策理由。

全局规则不要逐份复制——"不 revert 已有改动""不触发真实硬件/生产环境""不做计划外发散"这类直接引用 AGENTS.md 即可。禁区一节的价值在于记录**模型推不出来的东西**——设计约束、业务假设、格式限制这类信息。

## 分步计划
1. 步骤 1：...
2. 步骤 2：...

每步要可独立验证。**涉及不可逆操作时，必须拆成可分级门禁的步骤**（每一级显式开关，前一级不过不进下一级）。

## 验收点
- [ ] 编译/构建通过
- [ ] 相关单测通过（列出具体命令）
- [ ] 手动 smoke：...
- [ ] 无回归（指出最易回归的相邻功能）

## 风险预判
开工前已知的风险点，便于收口时对比。
```

## REPORT 必含字段

```markdown
# <阶段/步骤名>

**日期**：YYYY-MM-DD
**项目**：P<NN> <项目名>
**对应计划**：[总计划](plan.md)
**性质**：只读分析 / 实机验证 / 离线复算（写清有没有动硬件、有没有改代码）
**结论**：一句话

## 规格同步结果

三选一：已同步（规格链接与变更要点）／无需同步（具体原因）／待同步（缺项与下一步）。待同步时本次尚未全部收口，计划不能标已完成。审阅者对照实际改动核验，不能只看字段存在。

## 资料入口
| 资料 | 用途 | 位置 | 保存状态 |
|---|---|---|---|
| 清单 | 参数、输入输出、校验与归档信息 | 仓库相对路径或链接 | 本机/Git/外部归档核验结果 |
| 分析脚本、输入、结果 | 分别说明 | 实际路径或链接 | 分别说明 |

无额外资料时写“不适用”；资料详情以清单为准，不重复实测数据。

## 1. 数据来源与前提
用了哪批数据、什么条件下取的、有什么前提不成立就不能用这份结论。

## 2. 方法
可复核——注明所用脚本、参数、命令。别人照着能跑出同样的数。

## 3. 实测数据
表格为主。这是 report 存在的理由，也是它和 HANDOFF 的分界线。

## 4. 本次算不了的指标
明确写出来。没写的会被默认为"已验证"，这是最危险的误读。

## 5. 结论

## 6. 对下一步的建议
报告的价值不只是记录，是让下一次少走弯路。
```

## report 定稿后怎么改

**冻结的是数据，不是判断。** 分开看：

| 部分 | 性质 | 能否修改 |
|---|---|---|
| 数据来源与前提 / 方法 / 实测数据 / 本次算不了的指标 | 事实与当时的做法 | **不能**——改了就是造假，也让别人无法复核 |
| 结论 / 建议 | 对事实的解读 | **可以追加修订**，只追加不覆盖 |

冻结从**任务收口、report 定稿**那一刻开始。起草期间发现自己测错了（方法有误、脚本有 bug、数据取错），直接改，它还没定稿。

### 三种情况

**1. 数据没变，只是解读变了**（例如报告指出的缺陷后来被修掉了）
→ 在原 report 末尾追加「修订记录」，原结论**保留不动**：

```markdown
---
## 修订记录

### YYYY-MM-DD — <结论第 N 条已被修复处理>
<改了什么，附提交号>。
**本报告第 N 条描述的是修复前的状态，其数据仍然准确，但问题本身已不再成立。**
复测结果见 <新 report / HANDOFF 记录>。
```

**2. 重新测了，产生新数据**
→ 写**新 report**，命名加轮次（`round-02.report.md`），头部注明它更新了哪一份。旧的保留——它是"修复前基线"，正是它证明了问题存在过。数据不同就是两次不同的测量，塞进一份报告反而说不清哪个数对应哪个版本。

**3. 验收标准本身定错了**
→ 那是 `plan` 的事。**验收标准在 plan 里，验收结果在 report 里**——plan 可受控修订：追加原因、变更内容与用户确认记录，目标、范围或验收点变化重新确认后实施，不得为通过测试事后降低标准；report 记的是"上一次测出来什么"，改不了。

修订结论时，同时检查 HANDOFF 旧摘要、任务索引与规格的引用。在旧摘要附近追加日期和指向修订的链接，保留原文和原日期，不把更正只藏在最新日志里。

### 一句话

没有任何情况需要去改已定稿的实测数据。要改的永远是**对数据的判断**，或者**去测一次新的**。
