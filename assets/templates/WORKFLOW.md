# WORKFLOW.md — Task 协作流程

> 何时阅读：当一个改动够格立 **Task** 时（判据见 `AGENTS.md`「任务立项规则」：验证需要表格、多组实测数据或方法说明才讲得清；或涉及不可逆操作）。
> `AGENTS.md` 的强制命令区只列规则（采用 Claude Code 导入方案时，`CLAUDE.md` 通过 `@AGENTS.md` 导入同一份内容），本文件提供执行细节。

---

## 文档分工

同一件事只在一处是权威源，其余地方引用它、不复制它。副本必然漂移，这跟勤快无关。

| 位置 | 写什么 | 时态 | 写入时机 |
|------|--------|------|---------|
| `docs/specs/` | **系统是什么样**——各子系统的参数来源、算法与设计意图 | 现在时，长期有效 | 设计意图改变时 |
| `docs/tasks/` | **某段工作做了什么**——plan（做之前）+ report（做之后） | 有始有终 | 立 Task 时 |
| `docs/HANDOFF.md` | **每一轮发生了什么**——追加式流水 | 过去时，保留原文，可追加修订指引 | 每次提交前 |
| `docs/refs/` | 外部方提供的接口规格等参考资料 | — | 收到新资料时 |

跨项目的状态由 `docs/tasks/README.md` 的**项目登记表**承担，不另设状态文档——状态是从各 task 派生的数据，一旦另抄一份就会漂移。

接手时的读法：`docs/HANDOFF.md` 最上面 2～3 条看最近发生了什么 → `docs/tasks/README.md` 登记表看有哪些项目、各自到哪了 → 需要深入某个项目时读它的 `.index.md` → 需要知道某个子系统怎么运作时读 `docs/specs/`。

## 立 Task 的流程（plan → Worker → Review → report）

主对话只保留架构/审核/决策层的上下文，执行噪音隔离到 worker 里。

### 步骤 1：主对话对齐方案 → 落盘 plan

- 路径：`docs/tasks/P<NN>_<YYYYMMDD>_<任务名>/plan.md`
- 必含字段：
  - **目标**：要解决的具体问题
  - **边界**：可以动的范围
  - **禁区**：**只写本任务特有的约束**——全局规则引用 `AGENTS.md` 即可，不要逐份复制。这一节的价值在于沉淀模型推不出来的决策
  - **分步计划**：拆成可独立验证的小步。**涉及不可逆操作时必须拆成可分级门禁的步骤**，前一级不通过不进下一级
  - **验收点**：怎么算完成（编译通过 / 测试通过 / 手动 smoke 项）
- **计划未经确认不得分叉。**
- 模板与命名规则见 `docs/tasks/README.md`。

### 步骤 2：Agent 分叉 worker 执行 plan

给 worker 的 prompt 必须包含以下边界声明（参考模板）：

```
你的任务是按 docs/tasks/<任务目录>/plan.md 实现并验证，禁止：
- revert 已有改动
- 触发真实硬件调用或生产环境写操作
- 触碰 plan 中列出的禁区文件
- 做 plan 之外的产品发散
允许：dry-run、状态读取、UI wiring、单元测试、不触发真实硬件/生产环境的 smoke 测试。
```

worker 是冷启动的，plan 是它唯一的边界来源——**模型能力越强，一次能改的越多，没有边界时跑偏的代价越大**。

### 步骤 3：Worker 回归 → 五项摘要

worker 最终回复必须且只能包含：

1. 改动摘要
2. 修改文件列表
3. 验证命令和结果
4. 风险 / 未完成项
5. 明确确认未触碰禁区

主对话默认接收五项摘要，可按风险抽查关键 diff、测试输出和验收产物；摘要不替代证据。

### 步骤 4：主对话 review → 写 report + HANDOFF

review 不通过则让 worker 按已确认 plan 返工。若目标、范围或验收点确需改变，在 plan 追加修订原因、变更内容及用户确认记录，重新确认后实施；不得为通过测试事后降低验收标准。

review 通过后：

1. **写 `report.md`**（任务收口时）——数据来源与前提 / 方法（可复核，注明所用脚本与参数）/ 实测数据 / 本次算不了的指标 / 结论 / 对下一步的建议。
   定稿后**数据、方法与前提冻结**，**结论与建议可追加修订**——详见 `docs/tasks/README.md`「report 定稿后怎么改」。
2. **追加 `docs/HANDOFF.md`**——有 Task 的写**简版**：改了什么（1～2 句结论）/ 为什么 / 风险·未完成 / 指向这份 report。**详细数据只在 report 里写一次，HANDOFF 不重复。**
3. **记录规格同步结果**——检查本轮设计意图、契约或引用来源变化，同步对应规格。report 必须写明「已同步」（文件链接与要点）、「无需同步」（具体原因）或「待同步」（缺项及下一步）；审阅者对照实际改动核验。待同步时不能宣称全部收口或将计划标为已完成。
4. **更新 `docs/tasks/README.md` 项目登记表**的状态列；计划状态与验收边界分开，计划要求的验收未过不能标完成。
5. **核对任务资料**——从任务目录定位专用脚本、数据清单与结果；报告资料表能直接找到它们，参数/输入输出/校验与保存状态齐全。验证复测不会覆盖已有清单或结果，所引用脚本旧版本可以恢复；历史证据不能随工具升级重写。文件少时直接同放，不强制 tools/data 子目录；实际复用后再考虑公共工具，产品代码留源码，大型原始数据和既有共享脚本保留原位。格式见 `docs/tasks/README.md`。

## 不立 Task 的改动怎么办

绝大多数改动不立 Task。它们只需要一条完整的 HANDOFF 记录（改了什么 / 为什么 / 验证 / 下一步 / 风险），外加必要时同步 `docs/specs/`；在 HANDOFF「验证」段记录同样的规格同步结果，保留五段结构。

**判据不是改了几个文件，是验证产出的复杂度**：一句话说得清就不立 Task；非得靠表格、多组数据或方法说明才讲得清，就该立 Task——**不要硬塞进 HANDOFF**。

反过来也成立：**不值得写 report 的改动，也不该写 plan**。plan 和 report 成对存在，执行中暂缺 report 正常；已完成却缺报告需先核查收口证据，再复盘立项判断。

## 文档巡检清单

**什么时候跑**：完成一段工作后、提交前、或任何时候你觉得文档可能落后了。发一句「按 WORKFLOW 的巡检清单跑一遍」即可。

**执行权限**：用户要求只读检查或升级预览时，仅报告发现、拟修正位置与方案，不修改文件或配置。用户已明确授权修复时，在已确认范围内直接修复，无需逐项重复确认；超出范围再说明并确认。下文“补”“删”“追加修订”和“当场改掉”均受此边界约束。

这份清单是**主动**检查——已启用的 git pre-commit 只在提交时拦截源码变更未配 HANDOFF 文件更新；日志内容、规格语义和结论是否仍成立需要人工巡检，不能由文件存在性代替。

### A. 机械检查（跑命令，结果客观）

**A1. 本轮改了什么**

```bash
git status --short && echo "---" && git diff --stat HEAD
```

**A2. 冻结的决定有没有被动过**

```bash
python3 -m unittest tests.test_frozen_decisions
```

若本仓库尚未建立 `tests/test_frozen_decisions.py`，这一步跳过——识别出第一条需要锁死的参数时再建。红了不代表代码错了——代表有人正在改一条冻结的决定，回 `docs/specs/` 看它为什么是这个值，走完重新验证再同步断言。

**A3. 全仓 md 死链**

```bash
for f in README.md AGENTS.md CLAUDE.md docs/*.md docs/tasks/*.md docs/specs/*.md docs/refs/*.md; do
  d=$(dirname "$f")
  while read -r p; do
    case "$p" in http*|*\**|*\<*|"") continue;; esac
    [ -f "$d/$p" ] || echo "死链: $f -> $p"
  done < <(grep -oE '\]\([^)]+\.md\)' "$f" 2>/dev/null | sed -E 's/^\]\(//; s/\)$//')
done; echo "（无输出即通过）"
```

**A4. HANDOFF 是否严格日期倒序**

```bash
python3 -c "
import io,re
s=io.open('docs/HANDOFF.md',encoding='utf-8').read()
# 先跳过文件头部说明——头部的示例文字里就写着归档分界标记本身，
# 直接从头搜索会在示例处误判成真的分界，把下面所有真记录都截掉。
# 「追加新记录」标记只在真实内容区开始前出现一次，先定位到它，
# 再在它之后的部分找归档分界。
marker = '<!-- 在这条注释下方追加新记录，最新的在最上面 -->'
s = s.split(marker, 1)[-1] if marker in s else s
s = s.split('<!-- 归档分界：以下内容归档自旧格式历史记录', 1)[0]
recs=re.findall(r'^## (\d{4}-\d{2}-\d{2}(?: \d{2}:\d{2})?)',s,re.M)
k=[(r+' 00:00')[:16] for r in recs]
bad=[(k[i-1],k[i]) for i in range(1,len(k)) if k[i]>k[i-1]]
print(f'{len(recs)} 条记录，' + ('顺序正确' if not bad else f'顺序异常: {bad}'))"
```

若文件里合并了旧格式的历史记录（见 `docs/HANDOFF.md` 自己头部的说明），归档段落前会有一行固定的 `<!-- 归档分界：... -->` 注释——上面的脚本认这行来判断"检查到哪里为止"，归档段落本身按旧习惯是升序，不检查、不算异常。

**A5. 孤儿 Task**（状态已完成，却只有 plan 没有 report）

```bash
python3 tools/task_pairs.py
```

同任务目录的 `plan.md` / `report.md` 默认配对；阶段与历史平铺文件按完整前缀配对；阶段/复测报告用 `**对应计划**：[标签](plan.md)` 显式关联，兼容旧字段 `**计划**`。任务内 `index.md` 或历史同项目 `.index.md` 仅有一个明确计划链接时可关联其报告链接；多计划索引可在每个表格行明确唯一计划与该行报告，否则需逐报告声明。编号相同不足以配对，显式关联不要求同名基线；关联不证明全部阶段已经验收。

检查范围为任务根目录及一级 `P<编号>_.../` 任务目录中的直接文档，不递归扫描 results 等资料目录。Markdown 关联链接相对所在文档解析。

固定状态为草拟中、已确认、执行中、搁置、已废弃、已完成。规范状态可带附注，自由/矛盾状态列为 `REVIEW`，缺失列为 `MISSING`，不得把全部疑点称为违规。已完成计划缺报告需处理，其他状态允许暂缺。退出码 0 无疑点或无对象，1 有缺失/待确认，2 配置/读取错误。无对象需明确记录。

只读跨仓库检查与结构化输出：

```bash
python3 tools/task_pairs.py --root /path/to/repo --tasks docs/tasks --json
```

有已确认历史豁免时，可显式传 `--policy docs/tasks/pair-policy.json`（不会自动发现或生成；只读样本也可传外部绝对路径）。内容示例：

```json
{"version":1,"exemptions":[{"plan":"P01_20200101_历史任务.plan.md","reason":"启用报告规则前的历史任务，经确认不追补","source":"docs/tasks/README.md#历史豁免"}]}
```

`plan` 必须是相对 `--tasks` 任务根目录的精确文件路径（新结构如 `P25_20260907_任务名/plan.md`），`source` 必须指向仓库内现存文件，锚点用于人工定位决定。来源内容和授权范围还须人工核对；配置只豁免该计划缺报告，不豁免状态或无效关联。无依据的例外保留待确认，不为清零告警编造豁免；不从自由正文自动授权。JSON 保留状态原文、验收边界、关联和分类疑点。
发现已完成孤儿先查漏收口、错名或状态误标，按真实证据补报告；无法复原的证据标明缺失，不编造或删计划消警，再复盘立项是否过重。

**A6. specs 引用的代码符号是否还存在**

```bash
python3 tools/doc_symbols.py
```

统计源码文件、规格文件、引用和疑点数。退出码：0 为无疑点或无引用（`NO_OBJECTS`），1 为疑点，2 为配置或读取错误。无引用不等于规格已经验证。可用 `--root PATH`、重复 `--src DIR` / `--ext .py` 和 `--specs docs/specs` 覆盖配置；所有存在的默认候选源码目录都会扫描；显式 `--src` 任一目录缺失或没有匹配源码文件时返回 2。递归扫描规格 Markdown，排除所有大小写形式的 `README.md`。

这是词法检查：Python 排除注释和字符串，其他语言可能把注释或字符串当作符号；限定名只验证末段标识符存在，不证明类归属、调用关系或规格语义。文档写「不发送 X」等否定性描述会产生预期疑点，须逐条人工复核。

### B. 判断检查（要读代码和文档对比，机器判不了）

**B1. 改了源码但 HANDOFF 没有对应记录？**

对照 A1 的结果查 `docs/HANDOFF.md` 最上面几条。缺了就补——按有无 Task 分档，写法见 `AGENTS.md`「交接日志规则」。

**B2. 本轮改动涉及哪些 specs？里面的描述还准确吗？**

核对本轮 report（无 Task 则 HANDOFF「验证」段）的规格同步结果：是否明确已同步、无需同步或待同步，链接/原因是否与实际改动一致。缺少记录需补齐；待同步保留未完成状态。此检查为人工审阅，不代表 hook 已实现自动阻断。

符号词法疑点由 A6 提醒，这里只看机器判不了的：

- 文档描述的**机制**是否还成立（比如"固定值"是不是已经变成了"按配置区分"）
- 参数是否避免手工重复维护；必要值是否引用权威来源或自动生成，并标明来源与更新方式

> **设计意图、契约或引用来源改变**时同步文档；纯实现数值调整通常不必改。

**B3. 有没有 report 的结论已经被后续工作推翻？**

如果本轮修掉了某份 report 指出的问题，去那份 report 追加「修订记录」——**不要改它的数据和方法**，只追加对结论的修订。格式见 `docs/tasks/README.md`「report 定稿后怎么改」。同时检查引用它的旧 HANDOFF 摘要、任务索引和规格；旧摘要就近追加修订链接，保留原文与原日期，避免单条检索继续传播已纠正的判断。

**B4. `docs/tasks/README.md` 的项目登记表，状态列和各 plan 的状态字段一致吗？**

```bash
python3 tools/task_pairs.py --json
```

拿这个输出跟登记表对一眼。

**B5. `docs/specs/` 的「已知限制」「尚未验证」两节，有没有已经解决的？**

解决了就删——这两节的价值在于准确。留着过期条目比不写更糟，因为它会让人去修一个已经不存在的问题。

### C. 收尾

在已确认的修复范围内，发现的问题当场改掉，然后按 `AGENTS.md`「交接日志规则」把本轮巡检的结论写进 HANDOFF（如果巡检本身产生了改动）。
