- 任务立项规则：判据是**验证产出的复杂度**。一个改动的验证需要表格、多组实测数据或方法说明才讲得清时，它才够格立一个 **Task**；一句话说得清的，不立 Task，只写 HANDOFF。
  - **立 Task 就必须有 plan 和 report，二者成对，缺一不可。不值得写 report 的改动，也不该写 plan。**
  - `plan` 在动手前写（目标 / 边界 / 禁区 / 分步计划 / 验收点），必须先对齐方案再落盘，**未落盘不得开始实施**；目标、范围或验收点变更须在 plan 追加修订原因、变更内容与确认记录，重新确认后实施，不得为通过测试事后降低验收标准；
  - `report` 在任务收口时写（数据来源与前提 / 方法 / 实测数据 / 本次算不了的 / 结论 / 建议）。定稿后**数据、方法与前提不再修改**——它们是证据，改了就是造假、也无法复核；**结论与建议可以追加「修订记录」**，只追加不覆盖。重新测出新数据时写**新 report**，旧的保留为基线；
  - 执行中只有 plan 没有 report 是正常状态；状态与验收边界分开记录。“已完成”仅指计划范围已收口，不代表范围外硬件验收通过。一个总计划可显式关联多份阶段报告，规则见 `docs/tasks/README.md`。
  - 新任务默认集中在 `docs/tasks/P<编号>_<日期>_<任务名>/`：`plan.md`、`report.md` 与专用脚本、清单、结果按需同放，不强制 tools/data 子目录。实际复用后再考虑提取公共工具；产品代码留源码，大型原数据可原位引用。报告资料表注明用途、输入输出、参数、校验及保存状态，不批量迁移历史资料。
  - **例外（必立 Task，不看验证复杂度）**：涉及生产环境变更、外部系统的真实写操作、物理设备动作等不可逆操作。这类任务的分步计划必须拆成**可分级门禁**的步骤——前一级不通过不进下一级。
  - 判断不了时先问清楚再动手。路径与模板见 `docs/tasks/README.md`，流程见 `docs/WORKFLOW.md`；
- 分叉执行规则：立了 Task 的任务用子代理（worker）执行，主对话不参与执行细节。worker 回归后只回报五项：改动摘要 / 修改文件列表 / 验证结果 / 风险 / 是否触碰禁区。主对话负责审核，可按风险抽查关键 diff、测试输出和验收产物；
- 交接日志规则：**任何进入 git 提交的源码改动，提交前必须在 `docs/HANDOFF.md` 有对应记录**（追加，最新在最上，严格按日期倒序）。写法按有无 Task 分档：
  - **有 Task**：写简版——改了什么（1～2 句结论，不写实现细节）／ 为什么 ／ 风险·未完成 ／ 指向对应的 `report.md` 或阶段报告。**详细数据只在 report 里写一次，HANDOFF 不重复**；
  - **无 Task**：写完整五段——改了什么 ／ 为什么 ／ 验证 ／ 下一步 ／ 风险·未完成。
  - 报告结论被纠正时，检查旧 HANDOFF 摘要、索引及规格引用；在旧摘要就近追加修订链接，原文与原日期保留。
  - 「为什么」两档都必须完整保留，它是决策记录。**要压缩就压「改了什么」里的实现细节**——那些 `git show` 随时能看。
  - 自检信号：若「验证」非得靠表格、多组数据或方法说明才讲得清，说明这个改动本该立 Task，**不要硬塞进 HANDOFF**。
- 规格同步规则：修改源码后，必须检查 `docs/specs/` 中对应的规格文档是否需要同步。规格文档以**参数来源与设计意图**为主，避免手工复制易变的当前值。协议常量、单位、兼容性边界和验收阈值等必要值可引用权威来源或自动生成，并标明来源与更新方式；设计意图、契约或引用来源改变时同步，纯实现数值调整通常不必改文档。
  - **规格同步结果必须留痕**：有 Task 写在 report，无 Task 写在 HANDOFF 的「验证」段；三选一：「已同步」列出规格文件链接与变更要点；「无需同步」说明与本次改动对应的具体原因；「待同步」列出缺项及下一步。待同步时不得宣称本次全部收口或将计划标为已完成。审阅者对照实际改动核验记录与规格内容，不能仅检查字段存在；既有定稿报告不追补。此项为流程要求，当前 hook 不自动校验。
  写完或大改 specs 后应跑 `python3 tools/doc_symbols.py` 自检——这是符号词法检查，不能证明归属或规格语义；无引用不等于规格已验证，疑点需人工复核。
  已冻结的决定应当由测试断言守护（`tests/test_frozen_decisions.py`），而不是只写在文档里——尚无冻结决定清单时，识别出第一条需要锁死的参数时就建这个文件。
- 守卫文件在 `.githooks/pre-commit`。每个克隆需单独核验 `core.hooksPath` 与执行权限，文件存在不等于启用；已有其他 hook 配置时先确认整合方案，不直接覆盖。启用后拦截源码暂存变更（包括按项目语言配置匹配的任务脚本）未配 HANDOFF 文件更新的提交，但不能验证日志内容正确；可被 `--no-verify` 绕过。specs 同步的提醒层（第 2 层）待 `docs/specs/` 有实际内容后再补模块映射。
