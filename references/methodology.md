# 方法论说明：为什么这套规则长这样

这份文档是给初始化时的你（Claude）看的背景资料，用来在向用户解释规则、或者用户想调整某条规则时，能讲清楚"为什么"而不只是"是什么"。所有规则都来自一个真实项目里反复踩坑、修正、再踩坑的过程，不是凭空设计的。写入目标项目的文档要精简（见 assets/templates/），但你自己要理解这些道理，才能在用户提出"这条能不能改"时给出靠谱的判断，而不是机械地说"不行，规则就是这样"。

---

## 一、任务立项的判据：为什么是"验证复杂度"而不是"改动规模"

最早的版本判据是"改动超过 5 个文件或超过 30 分钟就要立项"。这条规则实测下来两头都错：

- 一次纯 UI 改动（49 行的计划文档）因为凑够了文件数被要求立项，但它的验证一句话就说得清，立项纯属仪式。
- 一次只改了 4 个文件的定量算法改动，因为没凑够文件数而没有立项，结果这个改动悄悄让"第 7 个及以后的项目"的报告曲线全部算不出来——**规模小、影响大，规模判据完全没抓住风险所在**。

问题出在判据挂在了错误的变量上。规模和风险不是一回事。改成"验证产出的复杂度"之后，两头都对了：验证一句话说得清的，不管碰几个文件都不用立项；验证需要表格、多组数据、方法说明才讲得清的，就算只改一行代码也要立项——因为"讲不清楚"本身就是风险的信号。

**例外条款**（不可逆操作一律立项，不看验证复杂度）是单独加的，因为不可逆操作的风险不体现在"验证复杂不复杂"上，而体现在"错了能不能改"上。这类任务还要求分步计划拆成**可分级门禁**的步骤——先离线模拟、再只读探测、再最小实机验证、再完整执行，每一级都要显式确认才能进下一级。这个设计在真实项目里救过一次场：一套分级验收流程让某个接口不存在的问题在"只读探测"级别就暴露了，如果没有分级，会一路做到"完整执行"级别、设备已经在真实运动时才炸。

## 二、为什么 plan 和 report 必须绑在同一个判据上

最早 plan 和 report 是分开判断的："改动大就写 plan""验证复杂就写 report"。这个设计产生了 11 份计划里 8 份没有报告的局面——判据不对齐，两种文档就会各自按自己的节奏产生，配不成对。

改成"立 Task 就必须两者都有"之后，孤儿文件（有计划没报告，或反过来）就变成了一个诊断信号：执行中暂缺报告属于正常进度；已完成任务缺报告或报告无对应计划才需要核查。先查漏收口、错名、状态误标并补真实证据，再复盘是否立项过重，不能删计划消除告警。这比"允许两者独立存在"要严格，但严格换来的是文档集合本身具有自我诊断能力。

## 三、report 冻结规则：为什么"数据不能改，结论可以改"这条区分很重要

最初的设计更简单粗暴："report 写完就不能改"。这条规则听起来很干净，但实测下来会导致 report 说谎——如果 report 指出的一个问题后来被修复了，而 report 本身不能改，那么它会一直陈述一个已经不存在的问题，误导后来的读者。

真正需要冻结的是**证据**（数据、方法、前提），不是**判断**（结论、建议）。证据一旦能改，report 作为"可复核的记录"这个存在价值就没了——今天写的数据，明天可能被悄悄改成迎合新结论的样子，谁还能信。但判断应该能随认知更新，用"追加修订记录、不覆盖原文"的方式——这样读者既能看到最新结论，也能看到当初为什么会得出旧结论，两者都是有价值的信息。

三种情况的区分（数据没变只是解读变了 / 重新测出新数据 / 验收标准本身定错了）对应三种不同的正确动作，混在一起处理会导致"改 report 该怎么改"变成每次都要重新讨论的问题。

## 四、为什么交接日志的判据必须"可机械验证"

最早的措辞是"完成一段**实质性**改动后更新日志"。"实质性"这个词是主观的，实测下来它导致过一次约 400 行的核心逻辑改动完全没有留下任何日志记录——不是没人想记，是"这算不算实质性"这个判断本身被跳过了，没有触发点。

改成"任何进入 git 提交的源码改动都必须有记录"之后，判据变得可以用 git hook 机械检查——不需要依赖任何人（包括 AI 自己）去判断"这次算不算实质性"，只要有源码改动，日志就是必需品。**机械守卫只检查暂存的源码变更是否配 HANDOFF 文件更新，不证明日志内容与本次改动对应。** 内容与立项判断仍需人工审核；删除和跨匹配范围重命名也应纳入源码变更检查。

分档写法（有 Task 简版 / 无 Task 完整版）是为了避免"强制记录"演变成"为了通过检查而写废话"——如果强制写完整五段，而这段改动已经有一份详细 report 了，日志会变成对 report 的重复劳动，重复劳动是文档腐烂的另一种形式（没人愿意维护两份一样的东西，最后两份都会过时）。

## 五、为什么规格文档"只写来源不写值"

规格文档最容易腐烂，因为它描述的是会变的东西（代码的具体参数），但更新文档的动力远不如更新代码强——代码不对会报错，文档不对没有任何提示。

"只写参数的来源和设计意图，不写此刻的值"把文档需要更新的触发条件从"任何一次数值调整"收窄到"设计意图改变"，这能减少重复维护。**这不是让文档变得不精确，而是让文档描述那些真正不容易过时的东西**——为什么这样设计、参数之间的依赖关系、这套设计背后的实验或教训。

对于确实需要锁死的具体数值（不是"这个函数的作用是什么"，而是"这个超时时间必须是 30 秒不能改"这种），不能指望文档去守——文档会被绕过、会被忽略。这类值应该写成测试断言，改了就红，逼着改动者要么走完重新验证的流程，要么明确知道自己在动一条冻结的决定。**测试断言是给代码看的，文档是给人看的，两者分工不同，不要用文档去做测试断言该做的事。**

规格文档写完要自检符号是否存在，是因为规格文档是这套体系里唯一没有天然验证环节的一层——代码有测试兜底，report 有实测数据兜底，规格文档全靠撰写者当时的记忆，最容易凭印象写错（真实项目里发生过：文档说某个逻辑是"某个类"实现的，而那个类其实只存在于撰写者自己刚写的另一份文档草稿里，从未真正写进代码）。

必要的协议常量、单位、兼容性边界和验收阈值仍可以呈现：引用权威来源或自动生成，写清来源与更新方式，不另造手工事实副本。设计意图、契约或引用来源变化时同步。符号脚本仅提供词法疑点，不能验证归属、算法行为或规格语义；无引用只表示没有检查对象。

## 六、为什么 worker 分叉时要求"边界声明"，而且这个要求会随模型变强而更重要

有一种直觉认为，模型能力越强，需要的约束应该越少——但实测的结论正相反。子代理（worker）是冷启动的，它对当前对话的全部上下文一无所知，plan 文件是它唯一知道"能做什么、不能做什么"的来源。模型能力越强，它一次性能做的改动就越大、越有主见——**这意味着没有边界的话，跑偏的代价随之增大，不是减小**。所以这条规则不会随时间过时，反而会越来越重要。

五项摘要用于减少执行噪音，不限制主对话按风险抽查 diff、测试输出与产物。返工按已确认计划执行；目标、范围或验收标准需变化时，在 plan 追加原因、变更内容和确认记录，重新确认后实施，避免事后修改标准来迎合结果。

## 七、git hook 为什么必须是仓库里的文件，不能只装在本地

`.git/hooks/` 目录本身不会随 `git clone` 一起分发——每个人克隆仓库后都要重新装一遍钩子，实际上等于没有强制力（没人会记得装）。把 hook 内容写成仓库里的普通文件（比如 `.githooks/pre-commit`），再通过 `git config core.hooksPath .githooks` 指向它，钩子内容就会随 `git checkout` 在不同分支间自然切换、随 `git clone` 自然分发给协作者——但 `core.hooksPath` 这条配置本身是**仓库级**的（存在 `.git/config` 里，不属于任何分支），每个人的本地仓库还是需要执行一次这行配置命令才能启用。该配置只作用于当前本地仓库，不是全局配置；每个克隆均需单独核验。初始化时要向用户强调这一点，否则钩子文件明明在仓库里却没有实际发挥作用。

因此交付应分开报告文件生成、目标配置启用、隔离实测结果。真实拦截测试在临时仓库执行，避免意外提交目标仓库已有暂存内容；隔离通过不代表目标仓库完成真实提交验收。已有其他 hooksPath 或 hook 时先确认整合方案，不能覆盖已有守卫。

## 八、为什么"目标文件已存在"不能一律"跳过、不覆盖"

本 skill 最初的设计是：初始化时如果发现目标文件已存在，一律跳过、不覆盖，理由是"保守、不破坏用户已有的工作"。这个直觉对大多数文件是对的，但对 `CLAUDE.md` 和 `docs/HANDOFF.md` 这两个文件是错的，而且这个错误在真实使用中真的发生过、没有任何提示地发生了。

**`CLAUDE.md` 的坑**：这个文件不是"存在就跳过"或"不存在就新建"这么简单——它很可能**已经有这四条规则的旧版本**（尤其是这个项目之前手工搭过一套更早期的类似体系时）。真实发生过的情况是：执行时把"任务立项规则""分叉执行规则"正确替换成了新版本，还新增了"规格同步规则"，但"交接日志规则"——四条里**唯一**决定 `HANDOFF.md` 该长什么样的那一条——被漏掉了，原样留着旧文字（"实质性改动"、要求维护 `PROJECT_STATUS.md`）。三条改对、一条没改，从执行者的角度看"大部分工作完成了"，于是照常汇报成功。但对最终效果来说，**这一条没改等于全白改**——`docs/HANDOFF.md` 之后几天新增的记录，延续的还是旧习惯，因为唯一会告诉后来者"格式变了"的地方压根没变。

这里的教训是：**"部分完成"在这类任务里不能算完成，必须有收尾自查去逐条核对，而不是做完几步就默认自己都做对了。** 四条规则要按概念逐条搜索旧版本（不能只按标题字符串精确匹配，旧版本的名字可能不一样），确认是"替换"而不是"新增在旁边"（两条讲同一件事但内容冲突的规则同时存在，比缺一条更糟，因为没人知道该听哪条），最后**回头 grep 一遍**看有没有已知的旧措辞残留。这道自查本身几秒钟就能跑完，却是唯一能在当场发现"漏了一条"的机会——错过这个窗口，就要等用户自己翻文件才会发现，像这次真实发生的一样，隔了好几天。

**`docs/HANDOFF.md` 的坑类似但更微妙**：这个文件存在，不代表它是"我们这套约定的 `HANDOFF.md`"——很可能是这个项目自己维护了几个月的开发日志，只是恰好也叫这个名字，用法却完全不同（按时间顺序从旧到新往下追加、自由格式，而不是"新记录插最前面、五段结构"）。这种情况下，`AGENTS.md` 里新写的规则和这份已存在的文件在"日志该往哪个方向长"这件事上是直接矛盾的——而且没有任何标记会提醒后来的人"这里规则变了"。**判断一个文件"是不是我们的约定"，要看它有没有那句标记注释、条目是否按有无 Task 分档，而不是只看文件名和路径是否匹配**。格式不匹配时，这是一个需要用户拍板的产品决策，不是可以自己悄悄决定、也不是可以直接忽略的边界情况。

最初处理这个决策时，默认做法是把旧文件整体改名归档成独立文件（比如 `docs/HANDOFF_历史.md`），`docs/HANDOFF.md` 从空白模板重新开始。这个做法解决了格式冲突，但真实用过一次后发现它引入了新问题：**多出一个文件本身就是一种轻微的漂移**——两份"交接日志"摆在同一个目录里，容易让人以为要分别维护，而且找"这段历史当时是怎么回事"要先想起来去开另一个文件。后来改成默认**合并进同一个 `docs/HANDOFF.md`，用一行固定的 `<!-- 归档分界：... -->` 注释隔开**——旧内容原样接在新记录下方，不整理不重写，只是不再是独立文件。为了不让这段旧内容（升序、自由格式）把巡检脚本的日期序检查搅乱，那道检查本身也要认这行分界注释、扫到这里就停。**这是同一类教训的又一次重复：解决一个冲突时顺手引入的新结构，本身也可能变成下一个要被发现、被修的漂移源。**

同样的兼容性判断也适用于已有 WORKFLOW、任务模板和工具。保留文件不等于与新规则兼容：需检查命令、状态、配对及审核约定，冲突解决前不更新入口到不兼容的新规则。本轮不实现通用模板升级，迁移范围须另行确认。

## 九、为什么规则写进 AGENTS.md 而不是 CLAUDE.md

本 skill 最初把四条规则直接写进 `CLAUDE.md`。这个选择有个隐藏假设：项目只会被 Claude 系列工具改动。真实情况是同一个项目经常被多种 AI 编程工具轮流碰——查证后发现，Claude Code 目前**不会自动读取 `AGENTS.md`**，只自动加载 `CLAUDE.md`；而 Codex 这类工具默认读的正是 `AGENTS.md`，不是 `CLAUDE.md`。如果规则只写在 `CLAUDE.md` 里，那就是"Claude Code 用户能看到规则，换一个工具打开同一个项目，规则完全消失"——不是规则没生效，是那个工具压根不知道有这份规则存在。

一个真实项目已经出现过这种情况的雏形：它的 `AGENTS.md` 只有一行"见 `CLAUDE.md`"，试图用一句提示语把两边接起来。这个方向本身是对的（意识到了要跨工具），但机制是错的——**"一句提示语"是软约定，不是机械保证**。它依赖读到这句话的工具愿不愿意、会不会真的照做；而且这个指向的方向也反了：`AGENTS.md` 是那个更"中性"、被多个工具默认识别的文件，真内容该放在这里，`CLAUDE.md` 才应该是那个"薄薄的适配层"。

查证还发现 Claude Code 官方本身就支持这个反过来的写法：在 `CLAUDE.md` 顶部写一行 `@AGENTS.md`，Claude Code 读取时会**机械展开**——把 `AGENTS.md` 的内容原样拉进来一起加载，不是"建议去看"，是"读这个文件等同于读了那个文件"。于是最终方案是：规则内容只存在于 `AGENTS.md` 一处，`CLAUDE.md` 只留一行导入。Codex 类工具直接读 `AGENTS.md` 就拿到完整规则；Claude Code 读 `CLAUDE.md` 通过导入机制拿到同一份内容。两边都不用"猜另一个文件里写了什么"，因为压根不存在"另一份"——只有一份内容，两个入口。

这条和"第八节"的教训是同一类问题的两次发作：**"存在一个文件"不代表"这个文件真的会被读到"。** 第八节是"文件存在但格式跟约定不兼容"，这一节是"文件存在但这个工具压根不会主动打开它"。两次教训指向同一个原则：不能假设"写进某个文件"就等于"规则生效了"，要去查这个假设在目标环境里到底成不成立。

## 关于"这套规则能不能简化"

如果用户在初始化过程中质疑某条规则太复杂、想要精简，值得反问的是：**这条规则解决的是哪个具体的失败场景？删掉它，那个场景会不会重新发生？** 上面九节里的每一条都对应一个真实发生过的失败——判据挂错变量导致高风险改动漏检、plan/report 判据不对齐导致孤儿文件、report 允许修改导致陈述过时信息、"实质性"这种主观词导致大改动零记录、文档写死数值导致漂移、worker 无边界导致跑偏代价随模型变强而增大、hook 只装本地导致形同虚设、初始化时"存在就跳过"导致四条规则改对三条却没人发现漏了一条、规则只写进单一工具认的文件导致换一个工具规则直接消失。这些都不是理论风险，是复现过的具体教训。如果用户想精简，帮他理解精简掉哪条就是在重新打开哪个口子，然后让他自己判断这个风险在他的项目里是否可以接受——这是一个可以讨论的权衡，不是不可动摇的教条。


## 九、为什么任务资料默认放在同一目录

资料跨目录依靠相同前缀查找，仍让读者频繁切换位置。新任务以目录承担归属，把 plan/report、专用脚本和小型结果集中保存；文件少时不强制 tools/data 子分类。实际复用后再考虑提取公共工具，产品代码留源码，大型原数据只引用，避免提前分类或复制版本分叉。报告提供资料入口，清单保留参数、输入输出、校验和保存状态；历史资料不批量搬迁。

文件仍在本机，不等于能随 clone 交接，更不等于外部备份完成。清单分别记录这三种状态，也明确无法保存或复算的材料。它帮助定位和核验，不承诺自动备份。

## 十、为什么关联和状态必须容纳阶段工作

一个总计划可以有多份阶段报告；按项目编号宽泛配对会漏掉独立任务，强求同名基线又会误报合法的阶段组织。因此默认按任务目录内 plan/report 配对，阶段和历史文件用完整前缀或显式计划链接，唯一总计划的索引提供兼容入口，歧义留给人工。

状态只表达计划是否收口，验收边界保存“离线完成、实机待验”等细节。若实机属于本次验收点，任务不能标完成。旧自由状态不批量改写，有证据的历史豁免显式配置，未知问题不以豁免掩盖。

## 十一、为什么更正要传到阅读入口，升级要保留项目决定

报告修订后，单独检索旧交接摘要仍可能读到原判断。保留原始记录并就近追加修订指引，兼顾追溯与当前使用；不覆盖历史证据。

开发仓库、已安装 skill 副本、目标项目生成文件是三个独立层级，没有自动同步。项目可能已有有效模块映射或明确不使用 CLAUDE.md 的决定。先只读对比、列出保留项与待确认项，再按确认范围更新，比模板直接覆盖更可靠。具体预览流程见 `references/upgrade-preview.md`。
